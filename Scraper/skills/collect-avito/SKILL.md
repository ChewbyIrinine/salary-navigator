# Сбор вакансий для T&L

Версия инструкции: 1.2, 26.10.2026. Корень проекта определяйте по наличию
`Scraper/extract.js`; не используйте пути, вкладки или session ID автора.
Для параметров неизвестного интерфейса сначала прочитайте фактический snapshot.

## Что прочитать

- Актуальный gstack `/browse` в среде исполнителя: весь браузерный доступ через него.
- [Проверенный Aside-процесс](../../ASIDE_WORKFLOW.md): фильтры, очередь,
  извлечение и остановки. Этот процесс проверен на пяти карточках 20.10 и
  использован в первой выгрузке 21.10; новая сессия требует проверки доступа.
- [Паспорт и навигация данных](../../../Data/README.md).
- [Контракт общей таблицы и публикация](../../../Data/dataset/README.md):
  прочитайте перед подготовкой экспорта и обновлением GitHub.

Старый Python-сборщик из `Scraper/LEGACY_GSTACK.md` — отдельный исторический способ
через браузер gstack. Он не является командой запуска Aside-процесса.
[PARALLEL_COLLECTION.md](../../PARALLEL_COLLECTION.md) содержит рекомендации,
не доказательство готового универсального параллельного сборщика.

## Вход

Нужны город/география, профессия и способ её выбора (точный фильтр или запрос),
остальные фильтры, режим отбора, лимит просмотра/сохранения, дополнительные поля,
новый output-каталог и ссылка на исходную задачу/исследование, если они есть.
Неясные существенные условия уточните. В рамках ясного задания новые
разрешения на каждый технический шаг не запрашивайте.

Режимы различаются: «первые N выдачи» сохраняет исходный порядок и неудобные
примеры; «N подходящих» требует заранее заданного правила, лимита просмотра
и журнала отклонений. Не заменяйте один режим другим.

Каждый сбор сохраняет все доступные характеристики карточек отдельными
колонками и полное описание. Город и регион — место размещения на сайте;
описание другого места работы их не меняет. Профессии/сегменты — условия
отбора. Не подменяйте их классификацией из описания.

## Выполнение

1. Убедитесь, что другой исполнитель не владеет тем же потоком Авито. Если
   владелец активен, не трогайте его вкладки, очередь, профиль и процессы;
   остановитесь до согласованной передачи владения. Не запускайте дополнительные
   сетевые проверки «для уверенности».
2. Перед новым сбором и каждым resume выполните из корня проекта:

   ```sh
   python3 Scraper/skills/collect-avito/scripts/preflight.py --probe-aside
   ```

   Повторяйте проверку и после обновления репозитория/навыка. Она не кеширует
   готовность, не открывает сайт, не меняет VPN и выводит подсказки по проблемам.
   При `NEEDS_SETUP` исправьте обнаруженную причину и повторите; не начинайте
   навигацию с непроверенным окружением. Подготовка локального конфига описана
   в [Scraper/README.md](../../README.md). Полный Xray-конфиг остаётся вне Git.
   `LOCAL_CHECKS_OK` — проверка локальных зависимостей и выбранного файла, не
   доказательство работающего маршрута. Для Happ сверяйте активный профиль и
   свежий журнал по [VPN_HAPP.md](../../VPN_HAPP.md) при первой обычной загрузке.
   При заявленной работе без туннеля подтвердите это условие; скрипт его не измеряет.
3. Создайте собственную Aside-сессию/вкладки по `/browse`. Не копируйте профиль
   или cookies. Подтвердите фактические город, профессию, запрос и остальные
   контролы. После смены города профессия может сброситься. Популярная текстовая
   подборка не равна точной профессии. URL не конструируйте догадками.
4. До карточек сохраните выдачу, выбранные контролы, время, исходные ранги и
   очередь уникальных ID. Зафиксируйте план/резерв. Используйте доверенный
   [extract.js](../../extract.js), сохранив его SHA-256 и Git-коммит, если есть.
   Поля неизвестного шаблона проверяйте по snapshot, не угадывайте.
5. Перед каждым переходом сохраните checkpoint: фильтры и их свидетельство,
   очередь, завершённые ID, следующий ID, состояние и причину остановки.
   Один владелец последовательно открывает наблюдённые ссылки карточек.
6. Прочитайте snapshot и выполните доверенный экстрактор в DOM. Проверьте
   `state=DETAIL` и точное совпадение ID. Сначала сохраните неизменяемый raw,
   snapshot и настоящий screenshot; затем производные данные и checkpoint.
   Передавайте файлы из текущего sandbox Aside обычными файловыми средствами;
   пути текущей сессии берите из её вывода. Не публикуйте сами session logs.
7. Локально проверьте JSON. Сохраняйте пары поле/значение и описание полностью,
   несколько значений и конфликты — раздельно. Период суммы, частота выплат,
   налоги и нагрузка различаются. Неизвестное не превращайте в ноль или месяц.
   `full_parameters_read` не выставляется автоматически по успешному JSON.parse.

## Остановка и продолжение

CAPTCHA, ограничение доступа, неожиданный ID или непонятная страница останавливают
новые переходы; сохраните состояние `NEEDS_HUMAN`/`REVIEW_REQUIRED` и причину.
Не извлекайте скрытое содержимое под блокировкой. Следуйте согласованной
политике ожидания; автоматического обхода блокировки в этом навыке нет.

При resume прочитайте существующий checkpoint и raw. Подтвердите ту же выборку
и текущую страницу по фактическому URL/ID. Вкладки и refs прошлого процесса
не переиспользуются вслепую. Не загружайте уже сохранённые ID повторно;
новое наблюдение того же ID храните отдельно с новым временем. Завершённый
каталог не продолжайте: новый сбор получает новый каталог.

## Выход и проверка

Основной результат для команды — **актуальный `Data/dataset/vacancies.csv`**,
общий для Analytics и ML. Сначала сохраните отдельный неизменяемый CSV сбора:
одна строка на уникальную принятую вакансию, параметры в отдельных колонках.
Его должно быть достаточно для `pd.read_csv(...)`, без чтения raw или паспорта
и без разбора JSON в ячейках. Сохраните ID, URL, время наблюдения, город,
профессии/сегменты отбора, исходную зарплатную строку, описание и ограничения.
При нескольких сегментах сохраните все значения через `; `, не дублируя вакансию.
Отсутствующие значения оставляйте пустыми, не подменяйте их нулём или «нет».
Обязательные колонки, допустимые статусы и служебные поля определены в
[контракте](../../../Data/dataset/README.md). Для схемы первой выгрузки есть
офлайн-преобразование `utils/flatten_export.py`; новую схему проверьте отдельно.
Ссылку на CSV добавьте в `Data/README.md`. Архив ниже — дополнительный материал,
он не должен быть обязательным для открытия готовой таблицы.

Обогащение из описания запускайте в согласованном объёме. При отсутствии
обогащения явно ставьте `enrichment_status=not_run`; при завершении —
`completed`, `enrichment_version` и `enriched_fields`. Для каждого заполненного
из описания поля сохраняйте `<поле>__source=description` и `<поле>__evidence`
с точной цитатой из сохранённого описания. `completed` с пустым списком означает,
что обработка выполнена, но новых значений не найдено. Ошибку отмечайте `failed`,
не публикуя частичные результаты как завершённые. Явные параметры не затирайте
выводами из описания; противоречия сохраняйте отдельно. Для исторических данных
без разметки происхождения допустим `unknown`.

`Data/avito_runs/<run_id>/`: raw, проверенные карточки, свидетельства и
`exports/` с CSV/JSON и сводками. План и описание набора храните отдельно в
`Scraper/runs/<run_id>/plan.json` и `manifest.json`; технические журналы и
checkpoint — локально в `Scraper/runs/<run_id>/diagnostics/`. В общий экспорт
их не включайте. Основной плоский CSV кладите в `exports/vacancies_flat.csv`,
не дублируйте его в корне Data. Макет описания —
[Scraper/templates/manifest.template.json](../../templates/manifest.template.json).
Зафиксируйте версию инструкции (Git-коммит или hash), схему полей, модель
агента/настройки если известны, план и факт, уникальные ID, ошибки и stop_reason.

Одна карточка проверяется локально:

```sh
python3 Scraper/skills/collect-avito/scripts/check_capture.py --raw <файл.json> --expected-id <ID>
```

Это проверка структуры и идентичности, не полноты чтения, репрезентативности
или правдивости работодателя. Финально сверяйте очередь и файлы, число
включений и уникальных ID, фактическое покрытие плана, описания и ограничения.
Сохранённое и принятое после проверки — разные числа. Ссылки на полученные
данные добавьте в исследование и задачу; людей/статусы не назначайте догадками.

## Общий датасет и PR

После проверки сборки добавьте запись своего экспорта в
`Data/dataset/sources.json`: run_id, source, путь, SHA-256, подтверждённые регионы
размещения `placement_regions` и статус обогащения по умолчанию. Новые поля
получают единые названия до регистрации; не создавайте синонимичные колонки
для уже существующей характеристики. Внутри сбора ID уникальны. Строки,
ожидающие проверки, остаются вне принятого CSV. `fit_review_required` допустим
для проверенной карточки с явным сомнением о соответствии срезу.

```sh
python3 utils/build_dataset.py
python3 -m unittest utils.test_build_dataset
python3 utils/build_dataset.py --check
```

Сборщик объединяет один или несколько зарегистрированных экспортов по
`source + id`, выбирает целиком последнее наблюдение, добавляет новые колонки
и сохраняет first_seen_at/last_seen_at/run_ids. Старые выгрузки не изменяются.
Не дописывайте строки в общий CSV вручную. При конфликтующих наблюдениях
с одинаковым временем разберите исходники; случайного победителя не выбирайте.

Обычный результат задания на сбор включает публикацию обновления через PR,
если пользователь не исключил GitHub. После успешных проверок создайте ветку
`codex/<run_id>`, добавьте только свои данные, реестр, общий CSV/manifest,
паспорт и каталог. Проверьте staged diff, выполните commit, push и создайте PR
в основную ветку. В PR укажите условия/время отбора, принятые ID, сколько новых
и повторных ключей, изменение колонок, обогащение и ограничения. Сообщите ссылку
и прикрепите PR к чату, если инструмент доступен. Без merge и публикации секретов.
Если задание явно включает создание PR, дополнительное подтверждение не нужно.
При недоступном GitHub сохраните проверенные локальные файлы и сообщите причину.

При параллельном изменении реестра обновите ветку, сохраните записи обоих
сборов и пересоберите CSV/manifest; их Git-конфликты разрешаются пересборкой.
Финально покажите размер общей таблицы, небольшой пример строк и результат
`--check`. Если установлен `.github/workflows/dataset.yml`, GitHub Actions
проверяет соответствие таблицы реестру и тесты. До его установки проверки
выполняются локально; готовый шаблон находится в `Scraper/templates/`.
