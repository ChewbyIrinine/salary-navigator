# Happ: Авито напрямую при включённом VPN

Исполнитель: ИИ-агент. Зафиксировано по диагностике 20.10.2026. Это инструкция по проверенному изменению и его контролю; новые настройки VPN при написании документа не применялись.

Нужный результат: подключения к `avito.ru`, `avito.st` и их поддоменам идут через `direct`, остальные направления продолжают использовать существующий VPN-маршрут. Одной записи в интерфейсе недостаточно: проверять реально сформированную конфигурацию и журнал текущего туннеля.

## Настройка в интерфейсе

В работающем Happ выбрать используемый профиль маршрутизации и добавить в «Напрямую / Direct»:

```text
domain:avito.ru
domain:avito.st
```

Доменные правила покрывают также поддомены, включая `www`. Ссылки вида `https://www.avito.ru/moskva/vakansii` в этот список не нужны: маршрут задаётся для домена, а не пути страницы. Существующие локальные IP-исключения сохранить.

В показанном пользователем интерфейсе «Глобальный прокси-сервер» был включён, порядок — `Block → Direct → Proxy`. Не добавлять Авито в Block. После выбора профиля штатно остановить и снова запустить туннель: интерфейс явно сообщал, что изменения применятся при следующем запуске TUNNEL.

Если свежий контроль показывает `proxy`, хотя в Direct стоят оба домена, повторное добавление URL не решает проблему. Проверить, какой профиль и конфигурация действительно загрузились. Точная внутренняя причина, почему Happ не применил ожидаемые исключения в исходном состоянии, не была установлена.

## Изменение, которое было подготовлено и импортировано

Пользователь импортировал отдельное подключение на основе полной сохранённой Xray-конфигурации своего подключения. В неё было добавлено одно правило в `routing.rules` перед правилами, отправляющими Авито в proxy:

```json
{
  "type": "field",
  "domain": ["domain:avito.ru", "domain:avito.st"],
  "outboundTag": "direct",
  "ruleTag": "avito-direct"
}
```

Это **фрагмент маршрутизации**, не полная конфигурация, не VLESS-ссылка и не самостоятельная подписка. В полной конфигурации должен существовать outbound с тегом `direct`. Существующие сервер, ключи, DNS, inbounds, outbounds и остальные правила были сохранены. Правило вставили после уже существовавшего глобального запрета UDP/443; этот запрет не добавлялся в ходе исправления. Поэтому подтверждённый результат относится к TCP: UDP/443 в журнале продолжал идти в `block`.

Полный подготовленный файл остался локально:

```text
/Users/ivan/Library/Application Support/Avito-Happ-Repair/avito-direct-xray.json
```

Резервная копия исходного подключения:

```text
/Users/ivan/Library/Application Support/Avito-Happ-Repair/original-xray.json
```

Полный файл содержит параметры подключения и не копируется в проект или чат. Он относится к подключению на момент диагностики: при смене/обновлении подписки заново проверить актуальность сервера и правил. Файл внутренних настроек `routeSettings.json` нельзя выдавать за импортируемую подписку. Конкретный путь импорта зависит от версии Happ; успешность импорта подтверждать содержимым новой конфигурации и журналом, а не названием пункта меню.

Скрипт prepare_xray_fix.py (локальный архив: `../Notes/Research/vpn_avito_2026-10-20/prepare_xray_fix.py`) документирует сделанное преобразование. Сам он не импортирует файл и не перезапускает туннель, а при существующей резервной копии отказывается перезаписывать её. Не запускать повторно как универсальное средство ремонта.

## Как проверить реальный маршрут

1. Зафиксировать, включён ли туннель, время его запуска и выбранное подключение. Проверять работающий экземпляр Happ, не старые файлы другой установки.
2. Прочитать свежесформированную конфигурацию подключения и проверить наличие правила для **обоих** доменов, порядок правил и существование outbound `direct`. `connectedConfigJson` — сохранённый снимок, не экспорт исполняющегося ядра: отдельно сопоставить время и последующий журнал.
3. Отметить текущую позицию/время в access.log работающего Tunnel. В Aside выполнить один обычный переход или согласованную загрузку. Для `avito.st` использовать ресурс, уже наблюдённый на странице, не придумывать URL и не запускать серию проб.
4. Сопоставить новую строку по времени, домену либо IP назначения. Ожидается `accepted tcp:...:443 [socks -> direct]`. При IP вместо имени сопоставить его с фактическим адресом нужного ресурса в этом же измерении. Одна произвольная строка `direct` или DNS-запрос не доказывают маршрут Авито.
5. Проверить отдельно документ `avito.ru` и статические ресурсы `avito.st`. География IP на стороннем сайте — дополнительный контроль; она не доказывает маршрут каждого домена.
6. В той же Aside-сессии проверить загрузку интерфейса и действие фильтра. Время HTML и время JS/шрифтов измерять отдельно через Resource/Navigation Timing; статус 0 сам по себе не объясняет ошибку.

В диагностике были обнаружены два каталога:

```text
~/Library/Group Containers/group.su.ffg.happ.plus
~/Library/Group Containers/group.su.ffg.happ.ruplus
```

Работающий процесс использовал `ruplus`. Старое исправление файлов в `plus` не подтверждало изменение текущего туннеля. Каталог определять по работающему процессу/открытому журналу и свежести подключения; не редактировать оба наугад. Не выводить полный plist/конфиг с ключами подключения, cookies или токенами.

## Что действительно подтвердили

- До исправления контрольный запрос к `www.avito.st` был сопоставлен со строкой `[socks -> proxy]`: исходная проверка (локальный архив: `../Notes/Research/vpn_avito_2026-10-20/route_probe_result.json`).
- После импорта правило `avito-direct` появилось в сохранённой конфигурации; контроль `www.avito.ru` показал `[socks -> direct]`, но страница ещё вернула ограничение IP: результат (локальный архив: `../Notes/Research/vpn_avito_2026-10-20/after_import_2026-10-20.json`).
- Позже журнал содержал TCP/direct к адресам статического CDN, одновременно UDP/443 блокировался: выборка (локальный архив: `../Notes/Research/vpn_avito_2026-10-20/comparison/current_static_routes.json`). Ранний файл `after_import_static_route_log.json` с пустыми совпадениями не является подтверждением успеха.
- В контролируемой фазе без VPN та же Aside-сессия также получила HTTP 429. Прямой внешний IPv4 совпадал с фазой VPN/direct; основные DNS-адреса Авито совпадали, CDN-ответы различались. Это не доказывает неисправность DNS: сравнение (локальный архив: `../Notes/Research/vpn_avito_2026-10-20/comparison/comparison_result.json`).
- После ручного прохождения CAPTCHA пользователь сообщил о восстановлении доступа. Последующий проход по пяти карточкам завершился без новой проверки: результат (локальный архив: `../Data/avito_runs/labor_five_2026-10-20/manifest.json`). Состояние туннеля в этом последнем прогоне отдельно не измерялось; им нельзя подменять сетевую проверку.

Следовательно, «проблема с IP» — повод проверить маршрут, но не доказательство его ошибки: ограничение может сохраниться и при direct, и без туннеля. При явном ограничении остановить новые переходы и дать пользователю восстановить ту же сессию. Не лечить это бесконечными перезагрузками.

## DNS и границы применимости

На исходных скриншотах: Fake DNS выключен, стратегия `IPIfNonMatch`, Remote DNS `DoU / 1.1.1.1`, Domestic DNS `DoU / 8.8.8.8`. Это исходные настройки пользователя, не установленный нами рецепт исправления. В сохранённой конфигурации встречались другие DNS-настройки; расхождение дополнительно требовало проверки актуальности источника. Успешное преобразование не меняло DNS.

Не менять одновременно DNS, QUIC, IP-правила и профиль: иначе результат нельзя связать с конкретным изменением. Если при подтверждённом TCP/direct остаются задержки, разбирать конкретные ресурсы, ошибки транспорта и DNS отдельно. Нет доказательства, что одно правило устраняет все прежние 30–60-секундные задержки, либо гарантирует доступ после смены IP и обновления подписки.
